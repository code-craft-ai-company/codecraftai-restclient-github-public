# Requirements

## Introduction

The `github-public-client` feature provides a typed REST client for the public
GitHub REST API. Unlike the hand-written venue clients in this family, the
client is **generated** — `GithubRestClientGenerator` consumes GitHub's
published OpenAPI description (`generation/specs/api-public.json`, ~16 MB) and
emits the top-level client, one API-group module per OpenAPI tag, and a schema
catalogue of `SchemaObject` subclasses.

Only two modules in the package are hand-written: `githubrestclientbase.py`
(GitHub authentication) and `generation/githubrestclientgenerator.py` (generator
configuration). Everything else carries the banner
`# Auto-generated by RestClientGenerator. DO NOT EDIT.` and is reproducible from
the spec.

The client is built on `RestClientBase` from `codecraftai-restclient-base` and
takes credentials from `codecraftai-credentials`. Generated methods accept
`aspects: Optional[AspectsRest] = None` so callers control retry, timeout, and
logging policy externally; when omitted the client's construction-time aspects
are used.

## Requirements

### Requirement 1: Authenticate Against the GitHub Public API

**User Story:** As a caller, I want to authenticate with either a personal
access token or basic credentials so that the same client serves both CI
tokens and legacy username/password flows.

#### Acceptance Criteria

1. WHEN a `GithubPublicRestClient` is constructed THE SYSTEM SHALL default the
   `Accept` header to `application/vnd.github.v3+json` without overwriting a
   caller-supplied `Accept`.
2. WHEN `authenticate()` is called with a `BasicCredential` THE SYSTEM SHALL
   attach an `Authorization: Basic <base64(username:password)>` header.
3. WHEN `authenticate()` is called with a `GithubTokenCredential` THE SYSTEM
   SHALL attach an `Authorization: Bearer <token>` header.
4. WHEN the credential is neither of the above but exposes a `token` or
   `access_token` attribute THE SYSTEM SHALL treat it as a bearer token.
5. WHEN the credential exposes neither token nor `username`/`password` THE
   SYSTEM SHALL raise `RuntimeError` naming the unsupported credential class.
6. THE SYSTEM SHALL build the authenticated `requests.Session` in
   `GithubRestClientBase.authenticate` and SHALL NOT issue a login round trip
   (GitHub authenticates per request via headers).

### Requirement 2: Cover the Public API Surface by Tag Group

**User Story:** As a caller, I want the GitHub surface partitioned into
discoverable groups so that I can reach an endpoint family without knowing its
raw path.

#### Acceptance Criteria

1. THE SYSTEM SHALL expose one `RestApiGroup` subclass per OpenAPI tag, named
   `<PascalTag>ApiGroup`, in `groups/<tagslug>.py`.
2. THE SYSTEM SHALL expose each group as a read-only property on
   `GithubPublicRestClient` named after the snake-cased tag — for example
   `client.repos`, `client.actions`, `client.code_scanning`, `client.rate_limit`.
3. THE SYSTEM SHALL construct every group eagerly in `__init__` and hold it in a
   `_grp_<tag>` attribute; group instances hold the owning client through a
   `weakref` supplied by `RestApiGroup`.
4. THE SYSTEM SHALL cover the endpoint families present in the spec, including
   `actions`, `activity`, `apps`, `billing`, `checks`, `codescanning`,
   `codespaces`, `copilot`, `dependabot`, `gists`, `git`, `issues`,
   `migrations`, `orgs`, `packages`, `pulls`, `reactions`, `repos`, `search`,
   `secretscanning`, `securityadvisories`, `teams`, and `users`.

### Requirement 3: Generate Method Signatures from the OpenAPI Operation

**User Story:** As a caller, I want generated methods to carry real parameter
names and types so that the client is usable without reading the OpenAPI spec.

#### Acceptance Criteria

1. WHEN an operation declares path parameters THE SYSTEM SHALL emit them as
   positional parameters and compose the leaf via `str.format` against a
   `leaf_template` literal.
2. WHEN an operation declares query parameters THE SYSTEM SHALL emit them as
   keyword-only parameters and SHALL omit any whose value is `None` from the
   request `params`.
3. WHEN an operation declares a request body THE SYSTEM SHALL emit a `body`
   parameter and pass it through to `perform_call`.
4. THE SYSTEM SHALL emit `exp_status`, `headers`, and `aspects` as keyword-only
   parameters on every generated method.
5. WHEN `exp_status` is not supplied THE SYSTEM SHALL default it to the 2xx
   status codes declared for that operation in the spec.
6. THE SYSTEM SHALL derive the method name from the operation's `operationId`,
   splitting on `/` to separate tag from method, and SHALL prefer a
   `method-name` override from `generation/specs/api-hints.json` when one exists
   for that path and HTTP method.

### Requirement 4: Type Responses Against a Generated Schema Catalogue

**User Story:** As a caller, I want responses returned as typed objects so that
field access is checkable rather than dictionary spelunking.

#### Acceptance Criteria

1. THE SYSTEM SHALL emit one `SchemaObject` subclass per named schema in
   `components.schemas`, with each property declared as a `Field(...)`
   descriptor carrying its type, `required` flag, and description.
2. WHEN an operation returns a single object with a resolvable schema THE
   SYSTEM SHALL return that `SchemaObject` type, constructed via `from_dict`.
3. WHEN an operation returns a list and declares `page`/`per_page` query
   parameters THE SYSTEM SHALL return `PagedList[<ItemType>]` built from the
   parsed items, the response headers, and the raw payload.
4. WHEN an operation returns a list without paging parameters THE SYSTEM SHALL
   return `List[<ItemType>]`.
5. WHEN a payload cannot be coerced to the target schema THE SYSTEM SHALL
   return the raw dictionary rather than raising, except that `SemanticError`
   SHALL propagate (`RestApiGroup._parse_item`).
6. WHEN an operation's response schema is not resolvable THE SYSTEM SHALL type
   the return as `Any` and return the decoded JSON.

### Requirement 5: Handle No-Content and Empty-Body Responses

**User Story:** As a caller, I want status-only endpoints to return cleanly so
that a 204 does not surface as a JSON decode error.

#### Acceptance Criteria

1. WHEN a response carries status 204 or 205 THE SYSTEM SHALL return `None`
   without attempting to decode a body.
2. WHEN a response carries status 202 with a zero-length body THE SYSTEM SHALL
   return `None`.
3. OTHERWISE THE SYSTEM SHALL decode the response body as JSON.

### Requirement 6: Pagination Through the Link Header

**User Story:** As a caller iterating a large collection, I want page
navigation metadata attached to the result so that I can advance without
re-parsing headers.

#### Acceptance Criteria

1. THE SYSTEM SHALL return `PagedList` for paged operations, exposing `items`,
   iteration, `len`, and indexing over the parsed items.
2. THE SYSTEM SHALL parse the response `Link` header into `next`, `prev`,
   `first`, and `last` relations, exposing `has_next`, `has_prev`, `next_page`,
   `prev_page`, `first_page`, and `last_page`.
3. THE SYSTEM SHALL default `page` to `1` and `per_page` to `30` on generated
   paged methods, matching the spec defaults.
4. THE SYSTEM SHALL NOT auto-follow the `next` relation inside a generated
   method; page advancement is caller-driven.

### Requirement 7: Aspects and Error Behaviour Delegated to the Base Client

**User Story:** As a caller, I want retry, timeout, and HTTP error
classification to behave identically to every other ccai REST client.

#### Acceptance Criteria

1. THE SYSTEM SHALL route every request through `RestClientBase.perform_call`,
   selecting the execution strategy from `aspects.action_pattern`.
2. WHEN `aspects` is `None` on a generated method THE SYSTEM SHALL fall back to
   the client's construction-time aspects (`client.aspects`).
3. WHEN a `headers` argument is supplied to a generated method THE SYSTEM SHALL
   send it in place of the client's default headers, not merged with them.
4. WHEN the response status is outside `exp_status` THE SYSTEM SHALL log the
   formatted error and raise the typed exception selected by
   `raise_for_http_status` from `codecraftai-errors`.
5. WHEN a call fails with `HttpForbiddenError` THE SYSTEM SHALL discard the
   session and re-authenticate exactly once before bubbling the failure.

### Requirement 8: Regenerate the Client from the Specification

**User Story:** As a maintainer, I want the client rebuilt from a refreshed
OpenAPI description so that GitHub API changes land without hand edits.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide `GithubRestClientGenerator` bound to
   `GithubRestClientBase` with `CLIENT_MODULE_ROOT`, `GROUP_MODULE_ROOT`, and
   `SCHEMA_MODULE_ROOT` rooted at `ccai.restclient.github.public`.
2. THE SYSTEM SHALL read the OpenAPI description from
   `generation/specs/api-public.json` and write output into the package root,
   `groups/`, and `schemas/`.
3. THE SYSTEM SHALL name the generated client class `GithubPublicRestClient`
   and write it to the lower-cased class name as a module file.
4. THE SYSTEM SHALL stamp every generated module with the
   `# Auto-generated by RestClientGenerator. DO NOT EDIT.` banner.
5. THE SYSTEM SHALL leave `githubrestclientbase.py` and the generator module
   itself untouched by a regeneration run.
